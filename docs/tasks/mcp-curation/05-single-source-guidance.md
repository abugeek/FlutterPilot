# 05 · One source for the agent guidance, checked against the real tools

**Branch:** `feat/guidance-source` · **Depends on:** 04 (tool names final)

## Problem

How to use FlutterPilot is written in several places, by hand:

| Where | Who reads it | Notes |
|---|---|---|
| `serverInstructions` in `lib/flutterpilot_server.dart` (~line 586) | every MCP client at `initialize`; many put it in the model's context every session | the most expensive text: keep it short |
| `flutterpilot_guide` prompt (`_registerPrompts()`, ~line 1548) | agents that fetch the prompt | long, lists tools by name |
| `skills/flutterpilot/SKILL.md` | agents with skills (Claude, Antigravity, Gemini) | names tools, has a mermaid workflow |
| `docs/AI_AGENTS.md` (15 KB) | people and agents reading docs | |
| `CLAUDE.md` (repo root) | agents working **on** FlutterPilot | also explains tools; not shipped to users |
| `README.md`, `site/` | people | |

They drift: a tool merged or renamed in one place stays in another (task 04
renames some). There is no test that the tool names these texts mention
exist.

## Goal

1. A test that every tool name and `tool(arg: ...)` mentioned in agent-facing
   text exists and has that argument. This is the main value; do it first.
2. The three texts the server or skill ships (`serverInstructions`, the guide
   prompt, `SKILL.md`) generated from one source, so a change is made once.
3. Size budgets for those texts.

## Design

### A. Name check (do this first, it stands alone)

`test/guidance_names_test.dart`:

- Inputs: `serverInstructions`, the guide prompt text (expose it as a const
  or getter so the test can read it without a client), every tool
  `description` and property `description`, and the files `CLAUDE.md`,
  `README.md`, `docs/*.md` (excluding `docs/field-test-findings.md`,
  `docs/tasks/**` and `ROADMAP.md`, which are history and may name old
  tools), `skills/flutterpilot/SKILL.md`.
- Find tool mentions: backticked identifiers matching
  `` `([a-z]+(?:_[a-z]+)+)(\(|`) `` that look like tool names, and
  `name(arg: ...)` / `name(arg:` patterns. Keep a small allowlist for
  snake_case words that aren't tools (CLI subcommands, file names,
  `flutter_test`, extension names); keep it in the test with a comment per
  entry.
- Assert: each mentioned tool is registered (or in task 04's
  `retiredTools`, in which case the test fails with "X was merged into Y;
  update the text" — retired names must not stay in docs).
- Assert: each `tool(arg: ...)` uses an argument the tool's schema has (or an
  alias from `param_aliases.dart`).
- The failure message names the file, the line and the bad mention.

Fix everything it finds in the same PR. Expect hits; that's the point.

### B. One source for the shipped texts

Source: `packages/flutterpilot_server/guidance/` with:

- `instructions.md`: what goes into `serverInstructions`. Plain text, short.
- `guide.md`: the prompt body.
- `skill.md`: the SKILL.md body (frontmatter generated by the script from a
  small header block, or kept in the file; your choice, document it).

Shared sections (e.g. "Find a widget by key, selector or visible text", the
batching rule) live in `guidance/partials/*.md` and are included with a
marker like `<!-- include: finding-widgets -->`. Keep the include mechanism
trivial (one regex, no nesting beyond one level).

Generator: `tool/generate_guidance.dart` writes

- `lib/src/generated/guidance.g.dart` with `const serverInstructions = '''...''';`
  and `const guidePrompt = '''...''';` (escape `'''` and `$`),
- `skills/flutterpilot/SKILL.md`.

`lib/flutterpilot_server.dart` imports the generated consts instead of
defining them. Generated files start with a "Generated by
tool/generate_guidance.dart, do not edit" line.

Freshness test (`test/guidance_generated_test.dart`): runs the generator in
memory and compares with the committed files; fails with "run dart run
tool/generate_guidance.dart". Same idea as keeping `TOOLS.generated.md` in
sync; check whether that one has a test and mirror it.

`docs/AI_AGENTS.md`, `CLAUDE.md`, `README.md`: **not** generated (people
edit them freely). They are covered by the name check (A) only. If
`AI_AGENTS.md` mostly repeats `guide.md`, propose in the PR replacing its
repeated part with a link to the generated SKILL.md; don't do it without the
maintainer's OK.

### C. Budgets

In `tool_registration_test.dart` (or the new test):

- `serverInstructions` ≤ its current size after your edits (measure, set the
  limit to that + 100 bytes, dated comment). It reaches the model in every
  session; it must only say what a tool description can't (start with
  `get_app_summary`, finding widgets, batching, trust the response).
- guide prompt and SKILL.md: a limit at current size + 10 %, to stop slow
  growth.

While moving the text, remove from `serverInstructions` anything already
said in a tool's description. Measure before/after and report.

## Tests

- A: passes after fixes; show it failing on base with the list of stale
  mentions it found (paste in the PR).
- B: freshness test; the server's `initialize` result still carries the
  instructions (add an assertion to an existing test that starts the server,
  or check via `fp_bridge.dart`'s initialize response manually).
- C: budget tests.
- e2e on a device (the server text changed).
- Evals: task 01 suite with `--compare`. Instructions changes can shift agent
  behaviour; pass rate must not drop.

## Don't

- Don't generate `CLAUDE.md` or `README.md`.
- Don't change the MCP prompt's name (`flutterpilot_guide`) or the skill's
  `name:` field: clients and users refer to them.
- Don't add a Markdown/template package dependency for the includes.

- [ ] e2e passes; evals not worse.
